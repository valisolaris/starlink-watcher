# work-kickoff: 作業開始プロトコル

成果物を作る作業は、必ず以下の6フェーズを**この順番で**実行する。
フェーズの省略・順序の入れ替えは禁止。各フェーズの「完了条件」を満たすまで次に進まない。
ユーザーが「急いで」「すぐやって」と言った場合も、フェーズ1と3の確認だけは省略しない(質問数を最小限にすることは可)。

---

## フェーズ1: 成功条件インタビュー

**目的**: 何ができたら成功なのかを、実装前に文章で確定させる。

**手順**:
1. ユーザーの依頼を読み、以下が明確かを判定する:
   - 成功条件(何ができたら完了か)
   - 技術的な前提(言語、環境、既存コードとの関係)
   - エッジケース(異常入力、空データ、失敗時の挙動)
   - トレードオフ(速度 vs 単純さ、汎用性 vs 具体性 など)
2. 不明な点だけを質問する。質問は最大5個まで。
   - **明白なことは質問しない**。依頼文・既存コード・CLAUDE.md から推測できることは推測し、「前提: 〜と解釈しました」と明記して確認に含める。
   - 悪い質問の例: 「プログラミング言語は何にしますか?」(リポジトリが Python なら聞くまでもない)
   - 良い質問の例: 「入力ファイルが存在しない場合、エラー終了と空結果のどちらが正しいですか?」
3. 回答を得たら(または最初から明確なら)、以下の XML 形式で仕様を提示する:

```xml
<task>1〜2文でタスクの要約</task>
<context>関係する既存コード・環境・前提の列挙</context>
<success_criteria>成功と判定できる条件を箇条書き(検証可能な形で書く)</success_criteria>
<constraints>守るべき制約(触ってはいけないファイル、使えないライブラリ、性能要件など)</constraints>
<done_definition>「このコマンドを実行してこの結果が出たら完了」という具体的な完了判定手順</done_definition>
```

4. 「この仕様で進めてよいですか?」と確認する。

**完了条件**: 上記 XML 仕様に対してユーザーの承認(「OK」「進めて」等)を得た。
**次フェーズへの移行条件**: 承認を得たら即フェーズ2へ。承認前にファイルを読む・変更するのは禁止(仕様確定に必要な最低限のファイル閲覧のみ可)。

---

## フェーズ2: 探索

**目的**: 変更対象と影響範囲を、コードを変更せずに把握する。

**手順**:
1. 仕様に関係するファイルを検索・閲覧する(Grep / Glob / Read)。
2. 以下を箇条書きでまとめる:
   - 関連ファイルの一覧と、それぞれの役割
   - 現状の挙動(該当機能が今どう動いているか)
   - 既存のテストの有無と場所
3. **NEVER: このフェーズではファイルを一切変更しない。** Edit / Write の使用は禁止。

**完了条件**: 上記の箇条書き(関連ファイル・現状挙動・既存テスト)を出力した。
**次フェーズへの移行条件**: まとめを出力したら、ユーザーの返答を待たずフェーズ3へ進んでよい。ただし探索で仕様と矛盾する事実(例: 前提にしていた関数が存在しない)を発見した場合は、フェーズ1に戻り仕様を修正・再承認する。

---

## フェーズ3: 計画

**目的**: 何をどう変えるかを承認してもらってから手を動かす。

**手順**:
1. **ALWAYS: 計画の策定は、変更ファイル数によらず必ず Agent ツール(`model:"fable"`、起動エラー時のみ `model:"opus"`)へ委譲する。** 本体モデルが自分で計画を書いてはならない。委譲プロンプトには次をすべて含める(サブエージェントは会話文脈を持たないため、省略すると計画の質が落ちる):
   - フェーズ1で承認された `<task>` 〜 `<done_definition>` の XML 仕様全文
   - フェーズ2の探索結果(関連ファイルの一覧と役割・現状の挙動・既存テストの有無)
   - 手順2の4点を成果物として求める指示
   - **NEVER**: 「小さい変更だから」「自明だから」「急ぎだから」は委譲省略の理由にならない。変更ファイル数・変更行数の多寡も理由にならない
   - Agent ツールを起動できない場合のみ、「Agent を起動できないため本体モデルで計画を書く」と明示した上で本体が策定する。ここでいう「起動エラー」とは、Agent ツールが利用できない・起動が拒否される・応答が空またはタイムアウトで得られない、のいずれかを指す(`model:"fable"` が起動エラーになった場合はまず `model:"opus"` を試し、それも駄目な場合に本体へ落とす)。**NEVER: 起動できない事実を伏せたまま本体が書かない。**
   - 利用クレジットの枯渇によるモデル起動拒否も、上記の「起動が拒否される」に含む。これはセッション内で回復しないため、同一セッション内では以後 `model:"fable"` を再試行せず `model:"opus"` を直接指定する(グローバル CLAUDE.md の「同じツールが2回失敗したら…その目的に限り固定する」と同じ考え方をモデル委譲に適用したもの)。
2. 委譲先が返した計画を、要約・短縮せずそのまま提示する。ただし提示の前に、返答が下記4点をすべて含むかを検査する。不足がある場合は、不足点を名指しして同じ Agent へ再策定を依頼する(再依頼は2回まで)。2回目でも不足する場合は、不完全なまま提示せず、何が欠けたかを報告してユーザーの判断を仰ぐ。この再依頼の対象は内容のある不完全な回答に限る。空応答・タイムアウトは手順1の起動エラーとして扱い、同じ Agent へ再依頼せず `model:"opus"`(それも駄目なら本体)へフォールバックする。**NEVER: 本体モデルが不足分を補筆しない。** 計画は以下の4点を含む(各項目の直下にある NEVER 行は制約であり、4点には数えない):
   - **変更ファイル一覧**: ファイルごとに「何を変えるか」を1行で。一覧の末尾に「合計Nファイル(テスト含む)」と必ず明記する
   - **追加テスト**: どのテストファイルに何を検証するテストを足すか。「テストを追加しない」計画は、フェーズ4手順4の条件(テスト不能な成果物)を満たす場合のみ提案できる
   - **NEVER**: 「自明な修正だから」「急ぎだから」「テスト基盤が未導入だから」はテスト省略の理由にならない。基盤がなければテストファイルごと新規追加する
   - **リスク**: この変更で壊れうる箇所、未知の部分
   - **代替案**: 検討した別のやり方と、採用しなかった理由(なければ「なし」と明記)
3. 「この計画で実装してよいですか?」と確認し、承認を待つ。フェーズ1の仕様承認はフェーズ3の承認を兼ねない。計画を提示したら応答をそこで必ず終了し、同じ応答内で実装を続けない。

**完了条件**: 計画に対するユーザーの明示的な承認を得た。
**次フェーズへの移行条件**: 承認を得たら即フェーズ4へ。**NEVER: 承認前に実装を始めない。** 計画に修正指示が来たら、修正版の計画を再提示して再度承認を待つ。

---

## フェーズ4: テスト先行

**目的**: 仕様が壊れたら失敗するテストを、実装より先に用意する。

**手順**:
1. `<success_criteria>` の各項目に対応するテストを書く。実装コードはまだ書かない。新規ファイルの場合のみ、import を通すための空スタブ(`raise NotImplementedError` のみの関数群)をこのフェーズで作成してよい。
2. テストを実行し、**失敗することを確認する**。出力をそのまま貼り、直後に「失敗: N件 / 成功: M件」の集計行を必ず書く。M が1以上の場合、各成功テストについて成功する理由を1文添える。
3. 失敗理由が「まだ実装していないから」であることを確認する。新規ファイルの ModuleNotFoundError は「未実装が理由」に含めてよい。それ以外の理由(テスト自体のバグ等)で失敗している場合は、テストを直してから再実行する。
4. テスト不能な成果物(ドキュメント、設定ファイル等)の場合のみ、テストの代わりに「完了確認チェックリスト」(検証手順の箇条書き)を提示して代替する。その際「テスト不能な成果物のためチェックリストで代替します」と明記する。

**完了条件**: 仕様の核心を検証する新規テストが「未実装が理由で」失敗することを実行出力付きで示した(またはチェックリストを提示した)。修正前から成功するテスト(不変条件・回帰ガード)は、成功する理由を1文添えれば同時に成功していてよい。
**次フェーズへの移行条件**: 完了条件を満たしたら、ユーザーの返答を待たずフェーズ5へ進んでよい。

---

## フェーズ5: 実装

**目的**: フェーズ4のテストがすべて通るまで実装する。

**手順**:
1. 計画に沿って実装し、テストを実行する。
2. テストが失敗したら、次の順で対応する:
   a. エラーログ・スタックトレースを読む
   b. **失敗の原因を1〜3文で説明する**(説明してから直す。当てずっぽうの修正を繰り返さない)
   c. 修正して再実行する
3. **NEVER: テストを通すためにテストを弱める・削除する・skip しない。** テスト自体が間違っていると判断した場合は、その根拠を説明してユーザーの承認を得てから修正する。ただし例外として、検証の厳しさを下げない修正(期待値の計算ミス・テスト環境設定の誤りの訂正)は、原因を1〜3文で説明すれば承認なしで直してよい。
4. 同じテストが3回連続で失敗したら、手を止めて状況(試したこと・仮説・行き詰まりの内容)を報告し、ユーザーの指示を待つ。
5. 実装中に計画外のファイル変更が必要だと判明したら、変更せずフェーズ3に戻って計画を修正・再承認する。

**完了条件**: フェーズ4のテスト全件と既存テストが通り、その実行出力を貼った。
**次フェーズへの移行条件**: 完了条件を満たしたら即フェーズ6へ。

---

## フェーズ6: 報告

**目的**: 何をして、何が確認済みで、何が未確認かを引き渡す。

**手順**: 以下の形式で報告する:
1. **変更点**: 変更したファイルと内容の要約
2. **証拠**: 実行したコマンドとその結果(テスト出力を含む)。「確認済み」と「未確認」を明示的に分けて書く。フェーズ4の修正前実行の結果を「失敗: N件 / 成功: M件」の形式で必ず記載し、Mが1以上の場合は各成功テストが修正前から成功していた理由を1文ずつ添える
3. **未確認リスク**: テストでカバーしていない挙動、動作未確認の環境、残っている懸念
4. **スコープ外の気づき**(省略禁止): 報告を書く前に変更したファイル全体を読み直し、スコープ外の問題(入力検証の欠如、エラー処理漏れ、dead code 等)を「場所・問題・推奨対応」で列挙する(なければ「なし」と明記)
5. **単純化レビューの提案**: 最後に必ず次を提案する:
   > 「単純化レビューを実行しますか? 今回の変更に対して、過剰な抽象化・dead code・不要になった依存がないかを見直し、削れるものを削ります。」

**完了条件**: 上記5点を含む報告を出力した。単純化レビューは提案のみ行い、ユーザーが承認した場合だけ実行する(実行する場合はフェーズ3の計画提示から従う)。
